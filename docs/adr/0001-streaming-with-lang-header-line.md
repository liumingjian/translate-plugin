# 翻译响应用「流式 + 首行语向标记」而非结构化 JSON

划词翻译要同时拿到两样东西：译文，以及模型识别出的语向（用于翻译卡片上的徽标）。显而易见的做法是让模型返回 `{"source_lang":..., "translation":...}` 这样的 JSON，但 JSON 无法在流式输出下逐字渲染 —— 要么放弃流式让用户干等整段译完，要么自己写一个能容忍半个转义字符的增量 JSON 解析器。我们改为约定一个极简的自定义协议：**响应第一行是 `EN>ZH` 形式的两个 ISO 639-1 大写码，第二行起全部是译文**。前端边流边把首行剥掉喂给语向徽标，其余直接追加进译文区。

## Considered Options

- **非流式 + `response_format: json_object`** —— 解析最稳，但长段落要等 3 秒以上才有任何反馈，在划词这种即时交互里体感不可接受。
- **流式 + 纯文本，放弃语向徽标** —— 最简单，但卡片就少了「模型认为这是什么语言」的反馈，而这正是「语言完全交给模型判定」这一决策的唯一可见证据。
- **流式 + 首行语向标记**（选中）—— 兼得体感与语向信息，代价是格式遵循度靠提示词保证。

## Consequences

- 格式约束靠提示词硬压，模型偶发不遵守。**必须有兜底**：首行不匹配 `^[A-Z]{2}>[A-Z]{2}$` 时，整个响应当作译文处理，徽标显示「自动」。
- 这个协议横跨三处 —— 提示词、service worker 的流式解析、翻译卡片的渲染。改动它需要三处同步，反悔成本不低。
- 换用不支持 SSE 流式的翻译服务时，本决策需要重新评估。
